### 2.4. До и после оптимизации загрузки (`synchronous_commit=off`)

В `db/connection.py::copy_rows` добавлено `SET LOCAL synchronous_commit=off` на
транзакцию массовой загрузки. **Чистого замера «после» на свободной машине нет** — все
прогоны после правки шли при конкуренции, и это видно по цифрам:

| | ДО правки<br>`818573ab…`, машина свободна | ПОД НАГРУЗКОЙ<br>`65f52a08…`, параллельно шли чужие процессы и `autovacuum` |
|---|---|---|
| нормализация (стадия) | 8.2 с | 9.6 с |
| загрузка нормализации | **10.3 с** | **30.0 с** |
| сравнение (стадия) | 7.6 с | 14.8 с |
| загрузка сравнения | **16.7 с** | **51.0 с** |
| агрегация (стадия) | 6.3 с | 5.3 с |
| цикл целиком | **71.4 с** | 166.8 с |
| `load average` при замере | не зафиксирован (первый прогон сессии) | 6.3–8.2 |

Обе строки — один и тот же код и один и тот же датасет. Разница в 2.3 раза объясняется
**очередью на WAL, а не кодом**: за сессию кластер записал **10.45 ГБ WAL**
(`pg_stat_wal`), а `wal_buffers_full = 477 687` — буферы WAL переполнялись, и каждая
массовая загрузка ждала записи. Поэтому числа из колонки «под нагрузкой» нельзя выдавать
за результат оптимизации: они измеряют очередь.

Вывод по разделу: `synchronous_commit=off` **снимает ожидание коммита, но не уменьшает
объём WAL**. Насколько он помогает, покажет только прогон на свободной машине — до этого
в таблице стоит честное «не измерено».

Отдельный контрольный прогон в **чистой базе** (создана с нуля, миграции с нуля, в ней нет
других прогонов и мёртвых кортежей; машина при этом была загружена, `load average` 7–9):

| Фаза | Время |
|---|---|
| нормализация (стадия) | 10.1 с |
| **загрузка нормализации** | **36.9 с** |
| сравнение (стадия) | 6.6 с |
| **загрузка сравнения** | **43.4 с** |
| агрегация (стадия) | 6.4 с |
| проверки | 4.1 с |
| цикл `→ SUCCEEDED` | 139.1 с |

Окна загрузки остались такими же большими, как и в «грязной» базе (37 и 43 с). Значит
**причина — конкуренция за диск и WAL на уровне машины, а не раздувание таблиц и не
параллельные прогоны в той же базе**. Раздувание таблиц влияет на другое — на латентность
чтения сводной (§3.2), и это отдельный эффект, который нельзя путать с этим.

### 2.5. Микрозамеры, которые изолируют механизм узкого места

Прогон целиком смешивает compute, WAL и кэш, поэтому узкое место проверено отдельно —
на тех же данных, через тот же код загрузчика (`db.connection.copy_rows`), но без
конкурирующих процессов. `load average` при замере 6.3–6.8; таблицы-приёмники
одноразовые, без индексов (индексы в проде добавляют время — это видно в разнице с
реальной загрузкой из §2.1).

| Замер | Результат |
|---|---|
| COPY 572 221 строки `normalized_rows` (171.5 МБ JSONL) | **18.6 с** = 30 770 строк/с |
| COPY 289 533 строки `comparison_rows` (116.9 МБ) | **7.9 с** = 36 630 строк/с |
| COPY 572 221 строки `pivot_membership` (21.9 МБ) | **4.4 с** = 129 520 строк/с |
| те же 20 000 строк, **по одному `INSERT`** | 2.02 с |
| те же 20 000 строк, **одним `COPY`** | **0.048 с** |
| **выигрыш COPY против построчного INSERT** | **×42** |

Отсюда два вывода, которые и объясняют устройство загрузчика:
1. построчные `INSERT` не вариант: на 20 тыс. строк они дают 2 с, то есть ~290 тыс.
   строк заняли бы около 30 с только на `INSERT`, без учёта индексов;
2. пропускная способность COPY на этой машине — десятки тысяч строк в секунду, а не
   сотни: **загрузка ~1.4 млн строк физически не может уложиться в секунды**, и именно
   она, а не расчёт, задаёт нижнюю границу цикла.

### 3.1. Почему pivot стоит ~0.8 с и почему это нестабильно

План запроса (`EXPLAIN (ANALYZE, BUFFERS)`) для `PATH × CHANGE_TYPE`:

```
GroupAggregate  (cost=32642.91..33668.00 rows=213 width=42) (actual time=3294.842..5173.741 rows=89.00 loops=1)
  Group Key: f.path, f.change_type
  Group Key: ()
  Buffers: shared read=5183 written=935
  ->  Sort  (cost=32642.91..32898.38 rows=102189 width=43) (actual time=3283.179..3976.820 rows=572221.00 loops=1)
        Sort Key: f.path, f.change_type
```

Видно две вещи:
* планировщик ожидает 102 189 строк, а получает **572 221** — оценка занижена в 5.6 раза;
* соединение фактов со связями и `count(DISTINCT app_id)` идут через сортировку 572 тыс.
  строк; именно она и стоит ~0.8 с.

Честный замер, который мы не стали прятать: **тот же разрез по сырым строкам
`comparison_rows` (`GROUP BY path, change_type`) дешевле датамарта.** Interleaved A/B,
8 пар подряд, чтобы порядок не решал исход:

| Вариант | Медиана | Разброс |
|---|---|---|
| факты + membership (то, что делает приложение) | **848 мс** | 765–2202 мс |
| `GROUP BY` по `comparison_rows` напрямую | **719 мс** | 410–3690 мс |

Вывод, который надо произносить именно так: **на этой машине латентность сводной
определяется состоянием кэша и объёмом мёртвых кортежей, а не выбором плана.** Разброс
внутри одного варианта (410–3690 мс на одном и том же запросе) больше, чем разница между
вариантами (18 %). Датамарт при этом даёт то, чего прямой `GROUP BY` не даёт: один и тот
же предикат обслуживает и ячейку сводной, и drill-down (проверено: числа совпадают),
и фильтры по продукту/партнёру/причине без повторной агрегации 289 тыс. строк.

Отдельно проверено, что быстрая часть пути действительно быстрая: с фильтром
(`VALUE_CHANGED` + `path_prefix`) сводная считается за **21 мс**, потому что предикат
отсекает данные до соединения.

### 3.2. Деградация после удаления прогонов (наблюдение, важное для эксплуатации)

После удаления трёх прогонов из базы `ca.pivot_membership` осталась с
**1 716 663 мёртвыми кортежами из 3.15 млн (54.6 %)** — `autovacuum` до неё ещё не дошёл.
Измеренный эффект на том же запросе сводной: медиана **7.34 с** (5 повторов:
15.5 / 6.9 / 4.0 / 9.7 / 7.3 с) вместо 0.76 с до удаления. Лечится обычным
`VACUUM (ANALYZE) ca.pivot_membership` — без блокировок на чтение. Практический вывод для
защиты: **не удаляйте прогоны перед демонстрацией** либо сразу vacuum'ьте; иначе сводная
перестаёт укладываться в «≤5 с обязательно».

## 5. GPU-режим: почему не проверен

Требование задачи — CPU-режим обязателен, GPU — архитектурное решение. На этой машине
GPU-путь **не подтверждён**, и мы не выдаём его за работающий:

* в окружении нет `cudf`/RAPIDS (не устанавливались);
* GTX 1650 Ti — Turing, 4 ГБ VRAM: объём в принципе достаточен для 290 тыс. строк, но
  установка RAPIDS занимает несколько ГБ, а свободного места на диске было ~6 ГБ на
  момент старта работы;
* архитектура к GPU готова: `worker/runner.py` запускает вычислительный подпроцесс как
  `python -m cudf.pandas -m change_analysis.worker.stage_runner …`, то есть акселератор
  включается в **новом** интерпретаторе до импорта pandas (`PLAN.md §18.1`), а CPU и GPU
  используют один и тот же контракт процедур;
* если `COMPUTE_BACKEND=cpu`, запрос GPU-прогона **отклоняется с объяснением**, а не
  выполняется молча на CPU.

Честная формулировка для защиты: «GPU-путь спроектирован и подключён точкой запуска, но
на нашем железе не измерен; поэтому все числа выше — CPU».
