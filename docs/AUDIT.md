# Журнал состязательных проверок

Здесь записано, что именно пытались сломать, чем это закончилось и что осталось
непроверенным. Цель — не «мы молодцы», а воспроизводимость: каждый пункт можно
перепроверить командой.

---

## 1. Входные форматы (JSON / XML / свой ридер)

**Что атаковали.** Расширения в разном регистре, смешанный набор файлов, несколько масок,
маска с `..` и абсолютным путём, дубли APP_ID, namespace в XML, mixed content, числа
вида `007` и `1e3`, BOM, cp1251, UTF-16, пустой файл, два корня, DOCTYPE с сущностями.

**Результат:**

| Атака | Итог |
|---|---|
| `*.json` при файлах `.XML` | понятная ошибка, **добавлена подсказка** с реально найденными расширениями |
| `../*.json`, `/etc/*.json`, пустая маска | `InvalidRequest` — обход пути закрыт |
| дубль APP_ID (`I1.json` + `I1.xml`) | ошибка с обоими путями |
| namespace `{urn:x}a` попадал в `PATH` | **исправлено**: имена приводятся к локальным |
| mixed content | `ValueError` с предложением своего ридера |
| cp1251 без объявления / два корня / мусор | понятная ошибка разбора |
| cp1251 и UTF-16 **с объявлением** | разбираются корректно |
| «billion laughs» (8 уровней сущностей) | блокируется лимитом Python 3.14, память не растёт |

**Независимая проверка эквивалентности** (свой кодировщик JSON→XML, не код агента):
4004 документа, **572 221 строка, 0 расхождений** между JSON- и XML-разбором.

**Проверено сквозным прогоном:** набор из двух пар, где один файл — заведомо битый XML.
Прогон завершается `FAILED`, а в сообщении и в журнале есть APP_ID и путь к файлу:
`BAD_INPUT I2: APP_ID=I2, file=…/RESULTS/BEFORE/I2.xml: unreadable response: Invalid XML:
no element found: line 1, column 11`. Молчаливого исключения заявки нет.

**Не проверено:** XML на 20 000 заявок; экзотические кодировки (EBCDIC, Shift-JIS);
смешанный датасет «часть пар в JSON, часть в XML» (маска поддерживает, прогон — нет).

## 3. Документация против кода

Написан `tools/check_doc_claims.py`: он читает истину из базы и из сборки тестов и
сверяет **16 конкретных утверждений** в README/CONTRIBUTING/STATUS/BENCHMARKS/
ARCHITECTURE_NOTE, а также ищет устаревшие фрагменты (старый счёт тестов, удалённые
`run_id`, прежний адрес машины). Инструмент включён в `scripts/verify.sh`.

Им найдено и исправлено:
* `README` утверждал «171 passed» — устарело, стало 280;
* `CONTRIBUTING` писал «2002 пары» без разряда — приведено к общему формату;
* `ARCHITECTURE_NOTE` утверждал «pandas нужен для соединений», хотя `pandas` в проекте
  **не импортируется вообще** — заменено на фактическое «чистый Python + SQL»;
* `DECISIONS` содержал старый IP машины.

Он же поймал бы любое будущее расхождение — это и есть смысл проверки.

## 3a. Блок «Независимое мнение ИИ»

**Что атаковали.** Отсутствие ключа, утечку секретов в пакет, выдуманные моделью
ссылки на evidence, невалидный ответ модели, поведение при транспортной ошибке.

| Атака | Результат |
|---|---|
| Без ключа (`LLM_API_KEY_ENV` указывает на пустую переменную) | `state=UNAVAILABLE` с причиной «переменная окружения … не задана или пуста»; HTTP-запроса не было |
| Пакет 22 КБ: есть ли ключ, логин, пароль, хеш пароля, исходный код | **ни одного** из перечисленного |
| Модель сослалась на несуществующий `E9999` | наблюдение отброшено, счётчик `dropped_evidence` увеличен |
| Наблюдение без поля `text` | **найдено при этой проверке:** отбрасывалось молча; добавлен счётчик `dropped_malformed`, он выводится в UI и в HTML |
| Транспортный таймаут | после этой проверки добавлена одна повторная попытка (наблюдали `ConnectTimeout` 60 с, следующий вызов — `DONE` за 6.7 с) |
| Ответ модели не является JSON | `state=ERROR` с текстом; в отчёте это отдельный блок, числа не затронуты |

Вывод: блок изолирован от детерминированных чисел и не выдумывает ответ при сбое.

## 4. Безопасность

| Атака | Результат |
|---|---|
| Проверка с `LABEL = '"><script>alert("xss")</script><img src=x onerror=...>'` | в HTML всё экранировано: `&lt;script&gt;`, `&#34;`; сырых тегов нет |
| Техническая ошибка в проверке (мой же баг `NameError: run`) | записана как `ERROR`, а не бизнес-`FAIL` — как требует контракт |
| Список проверок строится импортом пользовательского файла | **исправлено ранее**: `CHECK` читается через `ast`, без исполнения в веб-процессе |
| Путь вне `DATASET_ROOT` | `InvalidRequest` (проверено `../` и абсолютным путём) |
| Чужой прогон по прямому URL | `AccessDenied` во всех сервисах; проверено и пробником, и браузером |

**Не проверено:** исполнение заведомо вредоносного кода (в модели доверия хакатона это
вне объёма), ограничения по памяти на стадии сравнения для датасета 20 000 заявок.

## 5a. Красная команда: пять подтверждённых дефектов и что с ними сделано

Независимый аудитор (отдельная модель, только чтение) нашёл пять дефектов. Все
исправлены, на каждый есть регрессионный тест в `tests/unit/test_redteam_regressions.py`.

| № | Дефект | Тяжесть | Что сделано |
|---|---|---|---|
| 1 | Каталог проверки переиспользовался между ревизиями, а код выхода подпроцесса игнорировался: если проверка убивала свой интерпретатор, публиковался **старый** `result.json` как новый результат | ошибка данных | каталог `checks/<id>/rev<revision>`, старые `result.json`/`rows.json` удаляются до запуска, ненулевой код выхода → `ERROR` с хвостом stdout |
| 2 | XML: обычный атрибут `type="loan"` принимался за служебный маркер — атрибут исчезал, а `type="null"` **проглатывал содержимое элемента** | ошибка данных | служебным считается только атрибут в пространстве имён `{urn:change-analysis:types}type`; обычный `type` снова данные |
| 3 | Выход за `DATASET_ROOT` через соседний каталог с общим префиксом (`data` / `data-leak`): проверка была строковой (`startswith`) | блокер | принадлежность проверяется по разрешённым путям (`is_relative_to`) и в предпроверке датасета, и в worker |
| 4 | Проверка из файла **исполнялась при подготовке прогона**, в процессе веб-приложения | блокер | метаданные читаются через `ast`, файл исполняется только в отдельном интерпретаторе worker; путь вне `SCRIPT_ROOT` отклоняется |
| 5 | Валидация результатов молча превращала `CNT=1.9` в `1` и пропускала `APP_IDS` из другого прогона | ошибка данных | дробные счётчики отклоняются, worker передаёт в валидатор список заявок прогона |

Дополнительно аудитор отметил три утверждения, которые он не смог подтвердить:
* тест «CHECKS_ONLY не пересчитывает витрину» сравнивает **только количество строк** —
  подмена значения при том же количестве проходит незамеченной (принято в работу);
* исторические измерения в `BENCHMARKS` ссылаются на прогоны, которых в текущей базе уже
  нет — числа не перепроверяемы по БД (поэтому их источник указывается в самом документе);
* `ARCHITECTURE_NOTE` утверждал, что у проверок «нет доступа к БД, только `mart`» — код
  передаёт подпроцессу `DATABASE_URL` под ролью только для чтения. Формулировка исправлена:
  изоляция обеспечивается ролью БД, а не отсутствием драйвера.

Найден и устранён побочный эффект самих тестов: две сессии на одной тестовой базе удаляли
прогоны друг друга (сессионная уборка `name ~ '^qa-'`), из-за чего падало с нарушением
внешнего ключа в `run_events` и выглядело как поломка конвейера. Теперь убираются только
прогоны, созданные **до** старта сессии.

### Второй круг: что осталось незакрытым после первого

Повторная проверка тех же исправлений (уже по коду, без исполнения) подтвердила два
пункта и нашла три недоделки — они закрыты:

| Недоделка | Как закрыто |
|---|---|
| `discover_files` шёл по симлинкам: файл-ссылка внутри среза могла вести за пределы набора; то же для `manifest.json` | конечный путь проверяется на принадлежность каталогу; на это есть тест с ссылкой наружу |
| Подготовка прогона всё ещё импортировала **встроенные** проверки (`list_builtin_checks` → `exec_module`) | добавлен `list_builtin_checks_light`: id/метка/параметры читаются из AST, импорт остаётся только в тестах исполнения |
| Валидация не проверяла `CNT <= TOTAL`, а `_run_app_ids` при любой ошибке подключения возвращал `None`, **молча отключая** проверку чужих `APP_IDS` | `CNT > TOTAL` отклоняется; ошибка чтения заявок теперь валит проверку в `ERROR`, а не пропускает её |

## 6. Что осталось непроверенным (честно)

1. GPU-режим (нет RAPIDS под Python 3.14 и 4 ГБ VRAM) — осознанно вне объёма.
2. Масштаб 20 000 заявок: не запускался.
3. Установка на второй машине с другой ОС.
4. Холодный кэш: все замеры чтения — на прогретых страницах, кроме специально
   оговорённого случая «первая сводка после прогона».
5. Отчёт при **упавшем** `CHECKS_ONLY` (должен ли показывать последнюю опубликованную
   ревизию) — поведение есть, тестом не закреплено.
