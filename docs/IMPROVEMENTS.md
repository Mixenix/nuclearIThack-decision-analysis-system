# Что можно улучшить

Список для второго разработчика: честные ограничения текущей версии и кандидаты на
улучшение с оценкой пользы и риска. Ни один пункт не выдаётся за сделанный.

Легенда: **польза** — что это даст на защите или в эксплуатации; **риск** — чем можно
сломать; **где** — файлы, с которых начинать.

---

## A. Известные ограничения (сознательно не сделано)

| Что | Почему так | Что нужно, чтобы закрыть |
|---|---|---|
| **GPU-режим** — не реализован | `cudf.pandas` ускоряет pandas-код, которого в конвейере нет (чистый Python + SQL); узкое место — загрузка в PostgreSQL (46 % времени), а не вычисления; на машине 4 ГБ VRAM | Переписать нормализацию и сравнение на векторные операции cudf (DataFrame вместо построчного обхода), сверить результат с CPU на стабильном порядке |
| **Частичные отчёты при потоковой загрузке** | Пункт карточки помечен «не обязательно»; приоритет был у полного цикла и корректности | Приём файлов батчами, `processed_pairs` vs `expected_pairs`, публикация ревизии по завершённым парам, запрет сравнивать `CNT` обработанных с `TOTAL` датасета |
| **Масштаб 20 000 заявок** | Не запускался; 2002 — выданный набор | Синтетический набор с новыми APP_ID (явно помеченный как benchmark-only), замер фаз, тюнинг COPY/индексов |
| **Клиентские замеры в браузере** | Все числа — серверное время запроса, это нижняя граница | `performance.now()` вокруг действия + отправка метрики, либо Lighthouse |
| **Холодный кэш** | Все замеры — на прогретых страницах (кроме специально оговорённых) | Скрипт «перезапустить PostgreSQL → первый запрос» с фиксацией |
| **Установка на второй машине** | Проверено: пустой venv + пустая база на этой же машине | Прогон README на чистой ОС (другой дистрибутив) |
| **Одновременная работа двух пользователей «с числами»** | Проверена изоляция доступа (pytest + браузер), но не совместная нагрузка | Два прогона одновременно, замер отзывчивости UI во время чужого расчёта |

## B. Кандидаты на улучшение (по убыванию «польза / риск»)

### B1. Пагинация и предупреждение об обрезке в сводной
**Проблема.** Если раскладка даёт больше 600 ячеек, интерфейс молча оставляет 25 строк
по собственной сумме. Редкие изменения исчезают с экрана без объяснения.
**Польза.** Снимает вопрос «а почему я не вижу этот атрибут» на защите; честность.
**Риск.** Низкий — только UI.
**Где.** `src/change_analysis/ui/pages_explore.py` (функция `render_matrix`), сервис
`report.pivot` уже умеет отдавать всё.

### B2. Раскладка сводной в URL
**Проблема.** После перезагрузки страницы выбранные измерения и фильтры сбрасываются
(сам отчёт восстанавливается — это проверено).
**Польза.** Ссылку на конкретную раскладку можно дать коллеге и вставить в отчёт.
**Риск.** Низкий — состояние уже сериализуемо (`FilterSpec` + два списка измерений).
**Где.** `ui/pages_explore.py`.

### B3. Ретраи и бэкофф для вызова LLM
**Проблема.** Одна попытка на клик; при `429`/таймауте пользователь получает `ERROR`.
**Польза.** Демонстрация устойчивости; ответ модели — необязательный блок.
**Риск.** Низкий (блок изолирован), но нужен предохранитель от «долбить API».
**Где.** `src/change_analysis/llm/adapter.py`.

### B4. Формат обмена между стадиями
**Замер.** Запись `rows.jsonl` — 4.48 с из 9 с стадии нормализации: половина времени
стадии не про вычисления, а про сериализацию.
**Польза.** Реальное ускорение полного цикла без изменения логики.
**Риск.** Средний: меняется контракт между стадиями (сейчас JSONL — простой и
отлаживаемый). Нужен бенчмарк до/после и сохранение читаемости артефактов.
**Где.** `worker/stage_runner.py`, `worker/artifacts.py`, процедуры.

### B5. Изоляция исполнения пользовательского кода
**Проблема.** Список проверок уже читается через `ast` без импорта, но кнопка
«Проверить контракт» исполняет код в процессе веб-приложения (по явному действию
пользователя, без таймаута).
**Польза.** Исполнение чужого кода перестаёт быть способом заморозить UI.
**Риск.** Средний: нужен быстрый протокол «валидация в подпроцессе с таймаутом».
**Где.** `src/change_analysis/checks/loader.py`, `services/procedures.py`,
`ui/pages_workspace.py`.

### B6. Индексы и физическое состояние таблиц
**Замер.** `VACUUM` вернул сводную с 7.34 с к 0.88 с; мёртвые кортежи после удаления
прогонов стоят дороже любой настройки транзакций.
**Польза.** Предсказуемая латентность.
**Риск.** Низкий: регламент «удалять прогоны только с `VACUUM`» + периодический
`autovacuum` по расписанию вместо дефолтного.
**Где.** `worker/runner.py` (после публикации уже делается `ANALYZE`), `scripts/pg.sh`.

### B7. Форматы входа: расширить за пределы JSON/XML — **закрыто**
**Сделано:** JSON, JSONL/NDJSON, XML, YAML, TOML, INI, `.properties`, CSV/TSV;
архивы и сжатие (`.zip`, `.gz`, `.bz2`, `.xz`) снимаются прозрачно. Маски датасета по
умолчанию покрывают все расширения. Реализация — `procedures/spr_formats.py`,
тесты — `tests/unit/test_multi_format_readers.py`.
**Осталось:** Parquet/Arrow (нужен `pyarrow`), BSON/MessagePack, XLSX — не реализованы,
потому что тянут зависимости; подключаются тем же ридером, если понадобятся.
**Польза.** Прямо отвечает на требование заказчика «любой формат».
**Риск.** Низкий: ядро формата не знает, добавляется только процедура-ридер.
**Где.** `src/change_analysis/procedures/` + строка в `DECISIONS.md`.

### B8. Чистка артефактов и политика хранения
**Проблема.** Артефакты стадий копятся в `ARTIFACT_ROOT`; большие файлы чистятся, но
политика неявная.
**Польза.** Диск не кончается в самый неподходящий момент (уже случалось: 99 %).
**Риск.** Низкий.
**Где.** `worker/runner.py::_purge_large_artifacts`, `docs/DECISIONS.md`.

### B9. Отчёт при упавшем `CHECKS_ONLY`
**Проблема.** Если публикация новой ревизии отчёта упала, страница показывает
последнюю опубликованную — но поведение не покрыто тестом.
**Польза.** Убирает последнее «неизвестное» поведение в отчёте.
**Риск.** Низкий: нужен тест, а не переписывание.
**Где.** `services/checks.py`, `tests/e2e/`.

## C. Как выбирать, что делать

1. Сначала то, что видно на демонстрации (B1, B2) — дешёво и снимает вопросы.
2. Потом то, что усиливает главный аргумент «мы мерили и знаем узкое место» (B4, B6).
3. B5 — если проект будет жить дольше хакатона: это про безопасность, а не про демо.

Правило простое: любое изменение должно оставлять эталонный прогон на **502 / 385**
(отложенный — **248 / 186**) и не может требовать правки выданных файлов проверок.
