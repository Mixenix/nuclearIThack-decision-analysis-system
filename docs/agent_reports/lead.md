# Отчёт координатора (lead)

Дата: 2026-11-07. Роль: архитектура, интеграция, приёмка, публичные контракты.

## Участвующие требования

R01–R05, R07, R10–R15, R17, R19–R20 (координация и приёмка); R06, R08, R09 —
приёмка чужих зон.

## Что сделано этим блоком

1. **Среда и запуск.** Приложение поднято как два процесса (`main.py` на
   `0.0.0.0:8000`, `python -m change_analysis.worker.main`), PostgreSQL — локальный
   кластер на 55432 (`scripts/pg.sh`). `PUBLIC_BASE_URL=http://192.168.31.231:8000`.
   `DATASET_ROOT` возвращён к канонической копии внутри рабочей директории (другая
   копия пакета ломала показ исходного JSON).
2. **Конфигурация.** `.env` приведён к рабочему виду: порт 8000, внешний адрес,
   DeepSeek (`LLM_PROVIDER=deepseek`, `LLM_MODEL=deepseek-chat`,
   `LLM_API_KEY_ENV=DEEPSEEK_API_KEY`). В `config.py` значения из `.env` теперь
   попадают в `os.environ` процесса (иначе `llm_available()` не видел ключ);
   добавлено поле `llm_max_evidence`.
3. **Исправленные дефекты.**
   * `services/report.py::raw_json` — читал путь через реестр датасетов, поэтому
     после переименования/удаления датасета «исходный JSON» переставал
     открываться. Теперь приоритет у снимка самого прогона
     (`runs.snapshot.root_ref` + `slices`).
   * `db/connection.py::copy_rows` — массовая загрузка помечена
     `SET LOCAL synchronous_commit = off` (локально для транзакции загрузки:
     ожидание WAL-флаша на 290 тыс. строк ничего не даёт).
   * `checks/loader.py::list_script_checks` — список проверок строился
     ИМПОРТОМ пользовательских файлов в веб-процессе. Теперь `CHECK = {...}`
     читается через `ast` без исполнения кода; файлы без объявления `CHECK`
     (сами процедуры нормализации/сравнения/агрегации) в списке проверок больше
     не появляются. Это снимает риск «тяжёлый импорт заморозил UI».
   * `ui/pages_explore.py` — заголовки колонок сводной больше не наезжают друг на
     друга (truncate + tooltip).
4. **Проверка приёмки собственными средствами.** Написан и прогнан сквозной
   пробник через сервисный слой (тот же путь, что у UI): 26/26 проверок PASS —
   вход, датасет (2002 пары), создание прогона, worker, 289533 строки витрины,
   502 различия, 385 смен решения, **0 расхождений с эталоном организаторов по
   2002 заявкам**, pivot, drill-down (число в ячейке = размер множества),
   отчёт проверок (32 строки), HTML (абсолютные ссылки, без внешних ресурсов),
   изоляция второго пользователя (0 утечек).
5. **Браузерная проверка (Chromium, Playwright):** 13/13 PASS — вход → список
   прогонов → страница прогона (стадии, 502/385) → отчёт проверок → сводная →
   клик по числу → список заявок → карточка заявки с атрибутами и raw JSON.
   Отдельно проверено: «к коду» из журнала этапов открывает рабочую область с
   исполнявшимся файлом; создание новой проверки в рабочей области →
   «Выполнить на прогоне» → строка появилась в том же отчёте (4/4);
   блок «Независимое мнение ИИ» — реальный вызов DeepSeek, наблюдения со
   ссылками на evidence. Скриншоты: `docs/screens/`.
6. **Отложенные заявки.** Прогон на HOLDOUT (998 пар) дал 248 различий / 186 смен
   решения — совпадает с эталоном организаторов.
7. **Гигиена.** Удалены дубли прогонов (оставлены эталонный, holdout и свежий),
   освобождено ~7 ГБ; репозиторий пересобран заново: в него не попадают материалы
   организаторов (data/, checks/, examples/, HOLDOUT, эталон), ключи и артефакты.

## Зависимости и блокеры

* Организаторы: holdout прогоняется на защите их силами (у нас результат

  «не настроено» — числа и вердикты от этого не зависят.
