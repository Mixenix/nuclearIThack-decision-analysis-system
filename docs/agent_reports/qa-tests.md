2. **`tests/unit` — 186 тестов, без БД.**
   * сериализация (CONTRACTS.md §0): `true/false`, `null` vs строка `"NULL"`,
     пустая строка, числа, схлопывание `710.0 → "710"`, `PREFIX.CLASS.SUFFIX.KEY`,
     экранирование `|` в `ARRAY_KEY`;
   * массивы: составной ключ `available_offers` (product_id+type), `product_catalog`
     (mfo_id+product_id), `ext_data` по `body.action`, перестановка field-keyed и
     value-keyed массивов (нет ложных изменений), позиционный вектор
     (`scoring.value`) — изменение, дубль ключа → внятная ошибка, неизвестный
     массив → ошибка с PATH, технические исключения;
   * четыре типа изменения, `null → false` = VALUE_CHANGED, `null`/`"NULL"`/`""`/
     отсутствие не путаются, bool ≠ число, `710` = `710.0`, бакет внутри интервала
     сохраняет `DIFF_FLAG=1`, границы бакетов;

     TOP_OFFER по `rank`, правило выбора эталонного product_id, «нет продукта —

3. **`tests/integration` — 66 тестов, PostgreSQL.**
   * MartAPI: все фильтры по отдельности и в комбинации, пустой список = пустая
     выборка (не «без фильтра»), литеральные `%` и `_` в `path_prefix`,
     `count() == len(rows())`, `app_ids` уникальны/отсортированы/внутри прогона,
     `total_apps` = пары, схема строк/срезов ровно по контракту, неизвестный
     фильтр → `ValueError` с именем, привязка Mart к одному прогону;
   * пять выданных проверок исполняются **без изменения файлов** (sha256 до/после,
     `spec.code` побайтово равен файлу), числа перепроверяются независимым
     пересчётом через MartAPI, новая «пользовательская» проверка идёт тем же
     путём, сбойная проверка → технический `ERROR` (не бизнес `FAIL`),
     детерминизм повторного запуска;
   * отчёт проверок: единая таблица, `scope` «весь прогон», `app_ids_are_sample`,
     LOW только при малом числе срабатываний, счётчики HIGH/LOW/PASS/ERROR;
   * сводка/pivot/drill: числа равны эталону (2002/502/385), 8 карточек,
     каждая ячейка == её drill-down (постранично до конца), ячейки покрывают ровно

     читает run/отчёт/pivot/drill/export/карточку/процедуру/приватный датасет,
     конфигурации раздельные, `code_changed_since_run` ловится, замена процедуры
     через конфигурацию (workspace) без правки кода приложения.

## Найденные дефекты

1. **Диагностика нормализации терялась** — `procedures/spr_normalize.py`
   собирал `NormalizeResult` до запуска ленивого генератора строк, поэтому
   `diagnostics` был всегда пустым; `worker/runner.py` его вообще не сохранял.
   Симптом: битый JSON молча выкидывал заявку, прогон завершался `SUCCEEDED`.
   Я передал репродукцию лиду (unit-тесты с `xfail(strict=True)` кодировали
   требование карточки). **Исправлено** отдельным агентом; тесты теперь
   asserting-версии и зелёные: битый файл валит этап, в ошибке есть путь к файлу и
   `APP_ID`, диагностика пишется в журнал прогона.
2. **`runs.revision` расходился с ревизией витрины** — после `CHECKS_ONLY`
   сводная и сводка пустели, а публикация новой ревизии отчёта удаляла строки
   предыдущих. **Исправлено** лидом (`ca.runs.data_revision`,
   `services/report.py::data_revision()`, публикация отчёта одной транзакцией).
   Проверено моими тестами, включая два `CHECKS_ONLY` подряд.

Оба дефекта подтверждены тестами, оба закрыты; открытых дефектов приложения у
меня нет.

## Допущения и ограничения

* Suite намеренно поднимает **один настоящий прогон** на 2002 заявки (~110–130 с),
  поэтому `pytest tests` идёт ~2.5–3 минуты. Это плата за проверку того же кода,
  который исполняет worker, а не мока.
* Случаи, которых нет в выданном датасете (пути с `%`/`_`, отсутствие одобренных
  заявок, значения с `|`), проверяются на **синтетических** прогонах, засеянных
  через сервисы приложения — данные маленькие, но путь исполнения настоящий.
  Заявку на «боевые» числа они не заменяют: числа эталона проверяются на реальном
  прогоне отдельно.
* Один раз suite пострадал от наложения с прогоном лида на общей тестовой базе
  (`UniqueViolation` по `facts_index_uidx`) — с тех пор запуски тестовой БД
  согласуются, а фикстура чистит свои остатки.
* `-q` в этом окружении не печатает итоговую строку pytest; в отчёте указаны
  числа из прогонов без `-q`.
