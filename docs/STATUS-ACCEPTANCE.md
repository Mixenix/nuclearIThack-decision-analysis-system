# STATUS-ACCEPTANCE — приёмка по карточке задания

Документ отвечает на один вопрос: **каждое требование «Приёмки» карточки задания
проверено или нет, и чем именно**. Список требований взят из карточки
(`ПАКЕТ/ЗАДАНИЕ/Задание — Система анализа изменений.html`, раздел «Приёмка»)
дословно.

Правило заполнения: `PASS` ставится только там, где проверка **выполнена** и её
результат воспроизводим командой из последнего раздела. Если проверено не мной, а
другим участником, это указано явно с именем роли. «Не проверено» — это
`NOT_VERIFIED`, а не «наверное работает».

Проверял: QA-агент (`qa-tests`). Дата прогона: 2026-11-07.
Все автотесты идут против **отдельной** базы `change_analysis_test`; основная база
`change_analysis` для тестов только читается.

## 4. Найденные дефекты и их судьба

Оба дефекта ниже найдены этой приёмкой в `app/src/**` — зоне других владельцев,
поэтому сам я их не правил: передал лиду с репродукцией. На 2026-11-07 оба
исправлены, и исправления проверены тестами.

### 4.1. Диагностика нормализации не доходила до результата — исправлено

* Было: `procedures/spr_normalize.py` собирал `NormalizeResult` до запуска
  ленивого генератора строк, поэтому `diagnostics` материализовывался пустым;
  `worker/runner.py` вообще не сохранял `result["diagnostics"]`. Симптом: битый
  JSON в паре заявок не виден нигде, заявка молча исчезает из витрины, прогон
  завершается `SUCCEEDED` — прямое нарушение требования карточки «Повреждённый
  JSON / неполная пара → FAILED, с указанием имени файла/APP_ID».
* Стало: диагностика теперь общая с генератором (`diagnostics=diagnostics`),
  `stage_runner` возвращает её в `result.json`, `runner` пишет каждый диагноз в
  журнал прогона (уровень, код, `where`, сообщение) и валит этап, если среди
  диагнозов есть `ERROR`; в сообщении есть `APP_ID` и путь к файлу. Добавлен код
  `INCOMPLETE_PAIR` для отсутствующего файла пары.
* Проверено: `tests/unit/test_ingestion_errors.py::test_stage_runner_reports_failure_and_diagnostic_for_a_broken_pair`
  (этап возвращает `ok=False`, в ошибке путь к битому файлу и `APP_ID`, строки
  читаемой пары при этом сохранены), `::test_stage_runner_must_report_the_broken_pair_with_its_app_id`,
  `::test_procedure_must_report_the_undeclared_array_with_path_and_slice`.

### 4.2. `ca.runs.revision` и ревизия витрины расходились — исправлено

* Было: `CHECKS_ONLY` увеличивал `runs.revision`, а факты сводной оставались под
  старой ревизией → сводная и сводка пустели после применения новой проверки.
  Кроме того, публикация новой ревизии отчёта удаляла строки предыдущих ревизий.
* Стало: добавлена `ca.runs.data_revision` (`migrations/0003_data_revision.sql`),
  `services/report.py::data_revision()` используется в pivot/drill/`apps_page`/
  `summary`; `run_checks()` публикует отчёт одной транзакцией и **не** удаляет
  строки других ревизий; `CHECKS_ONLY` перепубликует весь настроенный набор
  проверок, а не только новую.
* Проверено: `tests/e2e/test_checks_only.py::test_checks_only_keeps_the_pivot_and_the_summary`
  (сводная и сводка не меняются после применения проверки),
  `::test_a_second_checks_only_does_not_drift` (два CHECKS_ONLY подряд: `revision`
  растёт до 3, `data_revision` не двигается, ревизии 1 и 2 остаются читаемыми,
  дублей строк нет), `::test_checks_only_keeps_the_results_of_the_checks_run_before`.

### 4.3. Наблюдение без дефекта: счётчик прогресса этапа

`run_steps.progress_done` для этапа `aggregate` считает **строки сравнения**
(≈290 000), а не пары заявок (2002), поэтому в журнале последний шаг показывает
«280 000 / 289 533», хотя прогон содержит 2002 пары. Это осознанно: страница
прогона не подписывает счётчик как «пары» и ведёт прогресс по этапам. Отмечено
здесь, чтобы никто не прочитал это как ошибку счёта.

## 5. Как воспроизвести

```bash
# 0) окружение: отдельная база (в основную базу тесты не пишут)
cd /home/mixantax/nuclearIThackWorkingDir/app

# 1) юнит-тесты (без БД): сериализация, массивы, четыре типа, слои разрезов, контракт проверок
.venv/bin/python -m pytest tests/unit -q

# 2) вся приёмка: интеграция + e2e (один реальный прогон на 2002 заявки, ~2 мин)
TEST_DATABASE_URL=postgresql://ca:ca@127.0.0.1:55432/change_analysis_test \
  .venv/bin/python -m pytest tests -q

# 3) приёмка живого приложения по HTTP + браузер (нужен запущенный web)
.venv/bin/python tools/acceptance_ui.py --base-url http://127.0.0.1:8000
#    exit 0 — всё проверенное прошло, 1 — есть FAIL, 2 — часть проверок не выполнена
```

`tests/conftest.py` принудительно ставит `DATABASE_URL = TEST_DATABASE_URL` до
первого `load_settings()`, а каждый teardown проходит через
`qa_support.assert_test_database()`: если DSN не указывает на тестовую базу,
удаление отказывается выполняться. Прогоны создаются с префиксом `qa-` и
удаляются своей же фикстурой.
