## 1. Стек и почему именно он

| Слой | Выбор | Почему | Чем платим |
|---|---|---|---|
| Интерфейс | **NiceGUI** (Python, server-side) | команда пишет на Python; одна кодовая база без отдельного фронтенд-билда; готовые таблицы, редактор, диалоги | не SPA: тяжёлые интерактивные виджеты делать дороже; всё состояние — на сервере (для этой задачи это плюс) |
| Расчёт | **чистый Python + SQL**, pandas не используется | разбор ответа — это обход дерева, а не табличная операция; соединение срезов и агрегация уже выражены SQL (`GROUPING SETS`, `COUNT(DISTINCT)`), поэтому pandas не даёт выигрыша на 289 тыс. строк и остаётся лишней зависимостью в образе (`grep -rn "import pandas" src/` → пусто) | нет готового DataFrame-API в процедурах: пользователь пишет обычный Python; GPU-путь потребует отдельного интерпретатора |
| Хранилище | **PostgreSQL** | команда знает SQL; нужны транзакции, очередь на `FOR UPDATE SKIP LOCKED`, индексы, `COPY` | нужен администрируемый сервер; альтернативой был DuckDB, но он слабее по части конкурентного доступа и очереди |
| Очередь | таблица `ca.jobs` в той же БД | одна точка правды, без внешнего брокера | очередь не вынесена в отдельный сервис (для одной машины не нужно) |
| Доступ к данным для проверок | **MartAPI поверх SQL** | выданные проверки требуют именно этот интерфейс | проверка исполняется в отдельном интерпретаторе с подключением под ролью только для чтения (`ca_ro`), поэтому `mart` — рекомендованный путь, но не единственный барьер: изоляция обеспечивается ролью БД, а не отсутствием драйвера |
| Экспорт | **Jinja2** | автоэскейп по умолчанию, читаемый шаблон | статический документ, интерактивность остаётся в приложении |

Что рассматривали и отвергли: отдельный React/Go (нет времени и нет выгоды), Celery/Redis
(лишний сервис при одной машине), ORM (на 289 тыс. строк нужен контроль над планом
запроса), Docker (по условию не требуется).

## 2. Хранение: три слоя, а не один

```
JSON-ответы СПР
   │ нормализация (пользовательская процедура)
   ▼
ca.normalized_rows      572 221 строк  вертикальный datamart, срез в поле SOURCE
   │ сравнение (пользовательская процедура)
   ▼
ca.comparison_rows      289 533 строк  внешнее соединение по (APP_ID, PATH, ARRAY_KEY)
   │ агрегация (пользовательская процедура)
   ▼
ca.pivot_facts           21 601 факт   измерения отчёта + счётчик уникальных заявок
ca.pivot_membership     572 221 строк  факт ↔ заявка, для перехода к деталям
```

Плюс плоские слои: `app_segments` (одна строка на заявку — то, чего ждут выданные
проверки) и `product_segments` (по продукту на срез — для честных продуктовых фильтров).

Почему так: задание требует вертикальную витрину как основную форму, а не горизонтальные
колонки; проверки требуют горизонтальный вид на уровне заявки. Эти два требования не
конфликтуют, если разделить слои — витрина остаётся вертикальной, а `comparison_rows` и
`app_segments` являются производными представлениями.

Ключевое следствие: **сумма счётчиков ячеек не равна числу заявок**. Поэтому все итоги и
карточки считают `COUNT(DISTINCT app_id)` по связям «факт↔заявка», а сумма ячеек
подписана как сумма.

## 3. Конкурентность

Три процесса: веб, воркер, PostgreSQL.

* Клик «Запустить» создаёт неизменяемый снимок параметров и запись `QUEUED`, ответ
  возвращается сразу; страница прогона опрашивает состояние раз в секунду.
* Воркер забирает задачу в короткой транзакции (`FOR UPDATE SKIP LOCKED`), держит lease и
  heartbeat; «сторож» переводит задачи с истёкшим lease в `INTERRUPTED`, поэтому ничего не
  висит в `RUNNING` вечно.
* Тяжёлая работа — только в дочерних процессах. Веб-процесс никогда не считает.
* Проверки идут в отдельных процессах под ролью БД **только на чтение**.
* Одновременных вычислительных процессов на один прогон — один; параллелить этапы
  бессмысленно, они зависимы.
* Два браузера — это две независимые сессии; состояние каждого читается из БД по токену,
  владение проверяется на сервере.

## 4. Пользовательские процедуры

Один контракт, два источника.

```python
PROCEDURE = {"id": ..., "label": ..., "stage": "normalize|compare|aggregate",
             "contract_version": 1, "params": {...}, "entrypoint": run}
def run(context, inputs, params): ...
```

* **Рабочая область** — текст в БД, правится в CodeMirror.
* **Файл** — `.py` из `SCRIPT_ROOT`.
* Оба пути идут через один загрузчик и одну проверку контракта; выданные проверки
  используют другой контракт (`CHECK`) и поставляются **без изменений**.
* `context` даёт `run_id`, `backend`, `log`, `progress`, каталог артефактов и чтение/запись
  таблиц — и **не даёт** ни БД, ни shell, ни секретов.
* На запуске сохраняется снимок кода и его хеш: правка кода после запуска не меняет
  задним числом то, что уже исполнилось, и интерфейс честно помечает расхождение.

Формат СПР (имена полей, режимы массивов, технические исключения, бакеты) живёт **только
в процедурах**. Ядро знает лишь табличный контракт — поэтому новый формат ответа
подключается новой процедурой, а не правкой приложения.

## 5. Инкрементальная загрузка

Не поддерживается. Расчёт идёт по завершённому набору, отчёт публикуется после
завершения, во время расчёта видны этапы, прогресс и журнал. Это разрешено карточкой
задания; частичный отчёт потребовал бы отдельной согласованной базы отсчёта, иначе
`CNT` обработанной части сравнивался бы с `TOTAL` всего набора.

## 6. Узкие места — измеренные, а не предполагаемые

1. **Загрузка 1.4 млн строк в PostgreSQL — 63 % времени прогона** (45.2 из 71.4 с;
   свободная машина; источник — `ca.run_steps` + `ca.run_events`; на каноническом прогоне
   при параллельной нагрузке то же окно занимает 32.8 + 41.6 + ~50 с, то есть 124 с из 157 с).
   Три окна загрузки: 10.3 с после нормализации, 16.7 с после сравнения, 18.2 с после
   агрегации. Лечение: `COPY` вместо построчных `INSERT` (измерено **×42**), `work_mem=64MB`,
   индексы только те, что нужны запросам. Правка `synchronous_commit=off` оставлена ради
   устойчивости к конкурентной записи — измеримого ускорения A/B не показал.
2. **Сводная таблица над 572 тыс. связей — медиана 762 мс** (`PATH × CHANGE_TYPE`,
   7 повторов, серверное время). Узкое место — соединение фактов со связями и сортировка
   572 тыс. строк. Лечение: `work_mem=64MB` — измерено **1086 → 756 мс** (−30 %);
   отдельный дешёвый путь для «одно число без измерений»; фильтрованный разрез считается
   за 21 мс. До цели «отлично» (0.5 с на открытие) не хватило ~1.7×. Отдельно измерено,
   что `GROUP BY` по сырым `comparison_rows` дешевле датамарта (719 против 848 мс,
   interleaved), но не даёт единого предиката для drill-down — см. `BENCHMARKS.md §3.1`.
3. **Запрос падал из-за JIT** (`libLLVM` отсутствует на машине) — отключили JIT; это
   записано в конфигурацию кластера, а не «исправлено на словах».
4. Проверка гипотезы «блочный COPY быстрее» **не подтвердилась** (разница в пределах
   шума), изменение откатили — см. `BENCHMARKS.md §4`. Зато подтвердилось главное:
   `COPY` против построчного `INSERT` даёт **×42** (0.048 против 2.02 с на 20 тыс. строк).

## 7. Ограничения и следующие шаги

* GPU-путь подключён точкой запуска (`python -m cudf.pandas -m …`), но **не измерен**:
  на машине нет RAPIDS. Честный следующий шаг — установить `cudf-pandas` и повторить
  раздел 2 `BENCHMARKS.md` на CPU и GPU с одинаковым кодом.
* Нет инкрементальной загрузки и частичных отчётов.
* Нет версионирования пользовательского кода (есть снимок на запуск и хеш).
* Изоляция пользовательского кода — процесс + роль только на чтение + таймаут. Это не
  песочница уровня ОС.
* Сводную можно ускорить: денормализовать измерения в связь «факт↔заявка», чтобы убрать
  соединение; либо кэшировать результат последней раскладки. Оценка — до ~2× на чтении,
  ценой ~1.5× места.
